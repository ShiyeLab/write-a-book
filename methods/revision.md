# 把反馈落实到稿件

适用于编辑反馈、作者意见或审读发现的问题。输入是明确版本的稿件、完整反馈及本轮允许改动的范围。先将反馈整理到 [任务表](../templates/review/task.md)，每项写清问题、位置、修改范围、保留项和验收方式。

先判断问题类型。证据不足需补材料或删除未经支持的判断；章节职责重复需在授权内调整结构；局部含混可直接定点编辑。指令误导多个单元时同步更新指令和 state 的现行入口，不只改眼前一句。局部问题无需重写全书，也不要求所有反馈只能改指令。

保全式润色先做信息清单，列标题、案例、数字、单位、论证步骤、操作编号、表格各行列、提示词块和图示文字。若输入来自 PDF 或 Word，按 [提取方法](text-extraction.md) 选择可选工具或外部工具，再对原件复核；只声明实际覆盖范围。缺内容时停止对应段落的保全判断，不能把空表格当完成。

编辑时保留未授权变动的信息，必要的拆句和重排要有明确目的。记录 [改动清单](../templates/review/changes.md) 的位置、改前问题、改后动作和理由。反馈要求超出允许边界时指出具体冲突，继续处理不受影响的部分。

改后逐条验收：该问题是否解决，保留项是否都还在，关联单元是否受影响。引用变化则重新机械核验；衔接变化则连前后段一起读。结果区分已改、待核、未改及理由。完整示例见 [反馈](../examples/polishing/feedback.md)、[保全检查](../examples/polishing/preservation.md) 和 [修改记录](../examples/polishing/changes.md)。

## 使已采纳反馈进入下一任务

用 [反馈表](../templates/review/feedback.md) 区分：这次修改、单书约定、体裁偏好、可推广方法。作者改一句不自动成为全项目规则。已授权采纳时，更新下一任务真正读取的 brief、任务文件、风格说明或材料包，state 指向有效版本及下一步文件。只写历史复盘或聊天记忆不算完成。

旧规则撤回时标明替代关系；未经采纳的建议保持建议状态。通用提升需要跨任务依据和授权，依据不足留在单书。教学过程见 [反馈与下次任务](../examples/getting-started/feedback.md)。
